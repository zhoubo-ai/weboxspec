# Feature Specification: WeBox 企业员工餐食订购平台

**Feature Branch**: 未创建；当前项目目录未初始化 Git，规格路径独立于分支。

**Feature Directory**: `specs/001-webox-meal-ordering`

**Created**: 2026-10-16

**Status**: 实施中 — T001–T094完成；47项AC通过，其他34项待执行或补全，见验收台账

**Input**: 用户指定依据项目目录中的 [AI Vibe Coding V3.0 - PRD.md](../../AI%20Vibe%20Coding%20V3.0%20-%20PRD.md)（V3.0，2026-03-24）生成规格；2026-10-16 补充要求：“无时间约束，所有可选功能都实现”。此补充优先于原文的时限和可选范围表述。

**Product Goal**: 让约 200 名企业员工在手机和电脑上完成选餐、配置和订餐，让食堂获得准确的备餐订单并管理每日菜单。

**修订依据**：用户已要求按参考文档差异修订并执行方案。原文来源、采用决策和待执行验收分别见 [requirements-source.md](requirements-source.md)、[decisions.md](decisions.md)、[acceptance.md](acceptance.md)。原文要求与项目补充规则分别记录。

**Scope**:

- 完整交付 MUST 覆盖 Tier 1、Tier 2、Tier 3 的全部功能，包括库存实时展示与扣减、AI 选餐助手和经营看板；47 条功能需求和 11 条成功标准全部适用。
- P1/P2/P3 仅表示实施顺序，不表示任何功能可以省略或推迟到本次交付之外。
- 用户明确不设开发或交付时间限制，原 PRD 的 1.5 小时挑战时限不适用；订餐截止时间、用户操作耗时和响应性能目标仍按业务规则与验收标准执行。
- 系统提供的内容全部为英文；用户地址等自由文本保留原文并安全处理，不强制翻译。本文面向需求评审者，以中文描述业务。
- 本期不包含在线支付、退款、配送路线跟踪、多企业运营、邮箱验证、找回密码及管理员自助注册。订单金额用于订餐记录与经营统计，不代表已实际收款。
- 用户原文规定的交付和技术约束继续有效，单独记录于 [delivery-constraints.md](delivery-constraints.md)，由后续规划承接。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 员工建立账号并持续访问个人空间 (Priority: P1)

员工使用邮箱注册并登录，刷新后继续使用自己的账号，得到明确的输入错误或登录失败提示；员工与管理员访问各自允许的功能。

**Why this priority**: 身份与访问边界是个人订单、偏好及后台管理的基础。

**Independent Test**: 使用一个新邮箱和一个管理员账号，单独验证注册、登录、刷新、退出及越权访问。

**Acceptance Scenarios**:

1. **Given** 邮箱尚未注册，**When** 员工提交格式正确的邮箱和符合密码要求的密码，**Then** 账号创建成功且可登录，不要求邮箱属于特定公司域名。
2. **Given** 已有注册邮箱，**When** 再次注册或输入错误密码登录，**Then** 用户看到明确英文反馈，且不会创建重复账号或获得登录状态。
3. **Given** 已登录员工，**When** 刷新页面或退出后再次访问个人页面，**Then** 刷新保持登录，退出后受限页面要求重新登录。
4. **Given** 员工或未登录访客，**When** 直接访问 Console 或尝试操作他人的订单、地址和偏好，**Then** 操作被拒绝，且不泄露他人数据；管理员可进入独立导航的 Console。
5. **Given** 无效邮箱、7 位密码、纯字母密码或超长输入，**When** 提交表单，**Then** 显示对应的英文校验信息，未产生账号；密码不会以原文保存在可查阅的账号资料中。

### User Story 2 - 浏览每日菜单并构建准确购物车 (Priority: P1)

员工浏览当日菜品，按菜系与关键词寻找餐食，查看成分、选择配置并调整购物车，随时知道总份数与准确金额。

**Why this priority**: 这是员工选餐和下单的主要入口。

**Independent Test**: 预置包含普通菜品、必选配置和付费加料的菜单，独立验证搜索、配置、价格与购物车变化。

**Acceptance Scenarios**:

1. **Given** 当日有已上架菜品，**When** 打开菜单或详情，**Then** 卡片显示图片、英文名称、两位小数的人民币价格和菜系；详情展示描述、蛋白质来源、过敏原、辣度与配置。
2. **Given** 菜单包含多个菜系，**When** 同时选择 `Chinese`、`Japanese` 并输入关键词，**Then** 结果属于所选任一菜系且名称或描述匹配关键词；无结果时显示可恢复的英文空状态。
3. **Given** `Classic Beef Burger` 有必选面胚与酱料，**When** 员工未完成必选项就尝试加入，**Then** 被要求补全；选择加料后立即展示包含加价的单价。
4. **Given** 同一汉堡存在不同配置，**When** 连续添加同配置两份、另一配置一份，**Then** 同配置合为数量 2 的条目，不同配置单独列出，配置与金额均准确。
5. **Given** 购物车内有多条菜品，**When** 调整数量、移除条目或快速多次添加，**Then** 每次成功添加增加一份、总份数和总价一致，达到 5 份时停止继续增加，减量后可继续添加。
6. **Given** `Tomato Pasta` 为 ¥26.50、芝士加价 ¥3.00，**When** 选择面型并加入两份含芝士意面，**Then** 单价为 ¥29.50、小计及无其他条目时的总价为 ¥59.00。

7. **Given** 员工甲有购物车草稿，**When** 刷新、关闭重开浏览器或退出后重新登录甲账号，**Then** 恢复原配置及份数并重新校验当前价格和可售性；登录乙账号看不到甲草稿，失效条目须处理后才能结算。

### User Story 3 - 完成下单并查看、取消个人订单 (Priority: P1)

员工检查结算明细，选择配送日期、餐次和地址，提交一次订单；随后能查看订单状态和历史，并取消尚待处理的订单。

**Why this priority**: 形成从选择到备餐记录的完整闭环。

**Independent Test**: 使用预置购物车和可订时段完成一次订单，再验证提交重试、历史详情与取消。

**Acceptance Scenarios**:

1. **Given** 有效购物车且所选餐次可订，**When** 员工检查默认配送日期、选择 `Lunch` 或 `Dinner` 并选用历史地址或输入新地址，**Then** 结算展示每项配置、数量、含加料的小计与总价。
2. **Given** 订单提交成功，**When** 显示结果，**Then** 员工看到唯一订单编号、配送日期、餐次、地址及 `Pending` 状态，新地址成为本人可再次选择的历史地址，已订购的购物车条目清空。
3. **Given** 同一次结算提交遇到网络延迟或结果丢失，**When** 员工连续点击或重试，**Then** 最终仅有一个订单，重试获得该订单结果，不产生多次订单或库存的重复扣减。
4. **Given** 员工已有历史订单且菜品后来被改名、改价或下架，**When** 查看订单列表与详情，**Then** 仅看到本人全部订单，历史名称、配置、单价、数量、小计、总价和配送信息保持下单时内容。
5. **Given** 本人的订单为 `Pending`，**When** 取消或重复取消，**Then** 最终为 `Cancelled` 且仅产生一次取消效果；`Confirmed`、`Completed` 和他人订单均不可由该员工取消。
6. **Given** 空购物车、空白地址、超过 200 字符的地址或过去的配送日期，**When** 尝试提交，**Then** 显示英文原因且不会产生订单。

### User Story 4 - 遵守数量、截单和重复订餐规则 (Priority: P2)

员工只能为允许的餐次提交不超过 5 份的有效订单；过了截单时间后，系统帮助员工切换到最近的可订时段，并避免同一餐次重复下单。

**Why this priority**: 保证食堂的备餐计划可执行，防止超量、过期和重复订餐。

**Independent Test**: 使用可控制的运营时间以及已有订单，验证时间边界、数量边界和同时提交。

**Acceptance Scenarios**:

1. **Given** 购物车已有 5 份，**When** 查看菜单添加按钮或购物车加号，**Then** 均不可增加且解释上限；即使绕过页面限制尝试提交 6 份，也不能生成订单。
2. **Given** 当日午餐截止前尚可订，**When** 运营时间到达 10:00 或员工在 10:30 提交当日午餐，**Then** 所选餐次切换到当日晚餐并显示英文通知；当日 15:00 及之后则切换到次日午餐。
3. **Given** 配送日为未来且所选餐次尚未截止，**When** 进入或提交结算，**Then** 保留原选择；已过期日期不会被悄悄当作当天订单处理。
4. **Given** 本人已在所选日期和餐次有 `Pending` 或 `Confirmed` 订单，**When** 进入结算或切换到该餐次，**Then** `Place Order` 变为 `View Existing Order`，点击打开已有订单；同时从不同页面提交也不会出现两个有效订单。
5. **Given** 同餐次订单已 `Cancelled` 或 `Completed` 且仍未截单，**When** 员工明确发起一笔新的结算，**Then** 可重新订餐；旧提交的重试仍返回旧订单。
6. **Given** 自动切换后目标日期没有所选菜品，或购物车内菜品已下架、价格或配置改变，**When** 提交，**Then** 明确列出需调整内容并保留购物车，不静默替换菜品或按未确认的新价格下单。

### User Story 5 - 保存饮食偏好并获得可控提醒 (Priority: P2)

员工保存自己的过敏原、偏好菜系、辣度、口味浓淡及预算，通过开关控制个性化展示，并自行决定是否继续选择含过敏原或超预算的餐食。

**Why this priority**: 降低日常选餐成本，同时让提醒与用户决定保持清晰。

**Independent Test**: 为一个员工设置偏好，对照开关状态、含过敏原菜品和不同金额的购物车进行验证。

**Acceptance Scenarios**:

1. **Given** 员工保存偏好，**When** 刷新或重新登录，**Then** 设置仍存在；非法预算如负数、下限大于上限不能保存并有英文反馈。
2. **Given** 员工标记 `Egg` 过敏且菜品包含 `Egg`，**When** 尝试加入购物车，**Then** 弹窗列出命中的过敏原；拒绝不改变购物车，选择继续才添加，菜品仍可在普通菜单中看到。
3. **Given** 员工偏好 `Japanese` 和 `None` 辣度，**When** 开启 `Recommended for Me`，**Then** 优先展示偏好菜系、在同一优先组中优先匹配辣度并高亮命中项；关闭时恢复默认顺序，不改变搜索和筛选条件。
4. **Given** 单餐预算上限为 ¥30.00，**When** 结算金额为 ¥30.01，**Then** 出现英文超预算提示但仍可提交；金额等于上限时不提示超出。

5. **Given** 基础菜品无 Egg、可选加料标记 Egg，且员工标记 Egg，**When** 不选该加料、再选择该加料或修改已有配置，**Then** 仅实际配置命中时提醒；新增匹配重新确认，拒绝保留原购物车。

### User Story 6 - 管理员维护菜品、每日供应并处理订单 (Priority: P2)

管理员通过 Console 管理菜品资料、上下架及指定日期的供应安排，并完成订单确认、完成标记和待处理订单取消，使员工所见菜单与食堂工作一致。

**Why this priority**: 菜品库会持续扩充，运营人员必须能持续维护真实可订菜单；最小订单处理能力落实 PRD 背景中的管理员职责。

**Independent Test**: 使用管理员账号新增一份带配置的菜品，安排今日和明日菜单，再通过员工账号核验可见性；使用预置订单独立验证状态变化。

**Acceptance Scenarios**:

1. **Given** 管理员已登录，**When** 进入 Console 菜品表格、搜索名称或按分类筛选，**Then** 可定位已有菜品，并可新增或编辑完整菜单资料及图片。
2. **Given** 管理员编辑价格、过敏原或必选/付费选项，**When** 保存有效内容，**Then** 员工随后打开详情可见更新；负价格、未知分类、缺失必填项或无效图片不能保存，显示英文原因。
3. **Given** 已上架菜品出现在每日菜单，**When** 管理员下架，**Then** 员工重新获取菜单后不再看到该菜品，购物车中的旧条目不能继续下单，历史订单不受影响。
4. **Given** 管理员进入每日菜单设置，**When** 保持默认次日或切换到当日、选择菜品并设置非负整数供应量，**Then** 指定日期安排被保存，只有已上架且被安排的菜品出现在该日菜单。
5. **Given** 项目按启动说明完成初始化，**When** 在当日尚未截单时打开员工端，**Then** 当日已有可用于完整订餐的菜单及供应数据，包含 PRD 示例中的菜品、选项与英文内容；截止后按订餐规则提示最近可订餐次。
6. **Given** 订单状态为 `Pending`，**When** 管理员依次确认、完成，**Then** 状态依次为 `Confirmed`、`Completed` 且员工可见；跳过确认、回退状态或确认/完成已取消订单均不允许。

7. **Given** 他人的 Pending 订单，**When** 管理员取消并重试，**Then** 返回同一 Cancelled 订单，原配送日库存只恢复一次；普通员工无权取消他人订单，管理员亦不能取消 Confirmed/Completed。
8. **Given** 干净数据与运营日期 D，**When** 初始化、修改菜品和供应、再执行初始化，**Then** 首次 D 与 D+1 各有九道菜、每道 20 份，重跑不覆盖修改、不重置占用或重复记录。
9. **Given** 可解码且像素合规的图片，**When** 上传 5,242,880 字节与 5,242,881 字节的文件，**Then** 前者通过大小校验，后者拒绝；替换失败保留旧图。

### User Story 7 - 查看准确剩余供应并避免超卖（Tier 3，必交付） (Priority: P3)

员工看到每日剩余数量、低库存和售罄提示；多名员工同时购买也不会超卖，取消后供应恢复。

**Why this priority**: 保证高峰期供应透明度与并发正确性，依赖订餐闭环，纳入完整交付与强制验收。

**Independent Test**: 为某菜品设置 3 份供应，由多个账号并行购买并在另一页面观察，再取消一个待处理订单。

**Acceptance Scenarios**:

1. **Given** 剩余量分别为 4、3、1、0，**When** 员工浏览菜单，**Then** 均展示数量，1–3 有低库存提示，0 显示售罄并不可添加或下单。
2. **Given** 仅剩 1 份且两名员工同时各买 1 份，**When** 提交，**Then** 最多一人成功，库存不为负；失败者知道具体不足菜品及可用数量，能调整后重新提交。
3. **Given** 多条目订单中有一个菜品库存不足，**When** 提交，**Then** 整单不创建，不扣除其他菜品库存，购物车保留。
4. **Given** 两名员工打开同一天菜单，**When** 一人下单或取消待处理订单，**Then** 另一人在无需手动刷新的情况下看到剩余量变化；重复提交或重复取消不重复扣减或恢复。

### User Story 8 - 用自然语言获得个性化选餐建议（Tier 3，必交付） (Priority: P3)

员工用英文描述当餐意愿，选餐助手结合偏好、当前菜单和近 7 天订餐记录，逐步提供带理由的可购买菜品卡片。

**Why this priority**: 提供用户要求的个性化选餐能力，依赖菜单、偏好、历史订单和库存，纳入完整交付与强制验收。

**Independent Test**: 准备含售罄、过敏原、近期购买与未购买菜品的菜单，用英文偏好描述检查推荐与直接加购。

**Acceptance Scenarios**:

1. **Given** 员工标记 `Dairy` 过敏且存在售罄菜品，**When** 请求推荐，**Then** 结果仅包含目标日期可售、未售罄且不含所标记过敏原的菜品，并结合菜系、辣度、口味和预算偏好解释理由。
2. **Given** 员工近 7 天曾点过部分菜品，**When** 有其他匹配候选，**Then** 优先推荐未点过的菜品；明确要求不重复时剔除指定期间已点菜品，候选不足时说明原因而不放宽过敏原限制。
3. **Given** 正常可用的选餐助手，**When** 员工提交英文描述，**Then** 推荐内容逐步呈现，每项为带英文理由的菜品卡片，可进入正常配置和加购流程。
4. **Given** 推荐服务不可用、超时或无匹配菜品，**When** 发起请求，**Then** 得到英文说明，可重试或返回普通菜单继续订餐，不出现虚构菜品或成功提示。

5. **Given** 员工标记 Egg，某菜基础标签无 Egg 但任一可选配置有 Egg，**When** 请求推荐，**Then** 整道菜被排除，模型或用户提示词不能放宽；普通菜单仍遵循实际所选配置提醒。

### User Story 9 - 管理员查看真实经营状况（Tier 3，必交付） (Priority: P3)

管理员在 Console 了解今日订单与收入、畅销菜品、餐次分布、七日趋势及低库存，刷新后获取真实变化。

**Why this priority**: 支持食堂经营判断，依赖真实订单与库存，纳入完整交付并独立验收。

**Independent Test**: 准备已知日期、状态、份数和金额的真实订单，对照人工计算核验各图表和库存预警。

**Acceptance Scenarios**:

1. **Given** 今日有不同状态订单，**When** 查看概览，**Then** 显示今日订单总数、收入、已完成数、待处理数、已取消数，统计口径可从看板上的英文说明理解。
2. **Given** 今日菜品有不同销量，**When** 查看排行和时段分布，**Then** 柱状图展示销量最高的至多 10 个菜品，餐次对比区分 `Lunch` 与 `Dinner`；七日折线图包含无订单日期的零值。
3. **Given** 有菜品剩余量为 0–3，**When** 查看库存预警，**Then** 列出这些菜品并区分售罄与低库存；新订单或取消发生后，通过自动更新或手动刷新得到最新真实统计。

4. **Given** D 配送的 Pending ¥10、Confirmed ¥20、Completed ¥30、Cancelled ¥40 四笔订单，另有 D 创建而 D+1 配送订单，**When** 查看 D 看板，**Then** 总数 4、待处理 2、完成 1、取消 1、收入 ¥30，排除 D+1 订单；只有完成订单计入销量。

### Edge Cases

- 在 09:59:59、10:00:00、14:59:59、15:00:00 和跨日时判断订餐窗口，以食堂运营时间为准，设备时钟不能绕过截单规则。
- 员工停留结算时越过截止时间：自动调整选择并明确通知；提交时才发现超时则保留购物车，要求确认变更后的日期和餐次后再提交，不悄悄配送到另一餐次。
- 自动切换后的目标餐次已有有效订单：展示 `View Existing Order`，不继续跳到更晚餐次来规避限制。
- 未来目标日期无菜单或某菜品未安排：显示无可订餐食或条目不可用原因，允许调整日期或购物车，不创建无法履约的订单。
- 同一员工同时从手机和电脑提交不同结算：同日同餐次最多保留一个有效订单；同一次提交的网络重试始终对应原订单。
- 取消与管理员确认同时发生：只能得到一次合法状态转换；最终确认的订单不可再取消，最终取消的订单不可再确认。
- 相同选项以不同点击顺序选入购物车仍视为相同配置；必选项缺失、过期或额外加价变更须重新确认。
- 图片加载失败显示有意义的替代说明；菜单为空、搜索无结果、请求失败时有英文状态与恢复入口。
- 超长、全空白或带特殊字符的输入不能改变业务规则、执行输入内容或暴露他人资料；输入失败不清空其他已填内容。
- 个性化开关不取消搜索或分类筛选；过敏原提醒不会静默隐藏普通菜单菜品，而 AI 推荐必须排除命中过敏原的菜品。
- 库存按日期和菜品共享，不因配置不同或午晚餐不同而额外复制供应；供应调整不能低于该日仍占用的数量。
- 库存中购物车不预留供应；菜品加购后售罄、断线恢复和取消重试时，都必须以最新可用量为准。
- 推荐无安全候选时返回空结果和说明，不能为凑足结果纳入售罄或过敏原冲突菜品。
- 演示日已经过 15:00 时遵守正常切换规则，不为演示放开过期订餐；可准备次日菜单用于继续演示。

## Requirements *(mandatory)*

### Functional Requirements

#### 共通体验与账号（Tier 1）

<a id="fr-001"></a>

- **FR-001**: 系统提供的页面、导航、菜品与配置内容、表单、校验、通知、图表及推荐理由 MUST 使用英文；人民币符号 `¥` 保留。用户自填邮箱、地址等自由文本按原文安全保存，不自动翻译，不将其视为系统文案语言缺陷。

<a id="fr-002"></a>

- **FR-002**: 员工注册、菜单、购物车、结算、偏好、订单及 AI 选餐流程 MUST 可在手机与桌面屏幕完成，关键操作可见且无需页面级横向滚动。

<a id="fr-003"></a>

- **FR-003**: 所有价格、配置加价、小计和总价 MUST 按人民币分准确计算，展示两位小数，购物车、结算与成功订单金额一致。

<a id="fr-004"></a>

- **FR-004**: 所有文本输入 MUST 有长度限制与安全处理；邮箱及地址最多 200 字符，搜索最多 50 字符，无效或超长输入提供英文反馈且不得执行输入内容。

<a id="fr-005"></a>

- **FR-005**: 系统 MUST 允许格式合法且唯一的邮箱注册，不强制公司域名；邮箱去除首尾空格并不区分大小写进行唯一性判断。

<a id="fr-006"></a>

- **FR-006**: 密码 MUST 为 8–128 个字符且包含字母与数字，不得以原文保存或对外显示；注册和登录失败必须给出明确英文反馈。

<a id="fr-007"></a>

- **FR-007**: 已登录用户 MUST 在刷新后保持身份，并能主动退出；退出后不能继续访问个人或管理功能。

<a id="fr-008"></a>

- **FR-008**: 系统 MUST 区分员工与管理员；公开注册仅创建员工，员工不可使用 Console 功能，任何用户不得读取或变更未经授权的个人记录。

<a id="fr-009"></a>

- **FR-009**: 已保存账号、偏好、地址、菜单安排、每日库存及订单 MUST 在正常重启和重新登录后保留；员工的账号资料、偏好、地址和订单按所属用户隔离，菜单与每日库存作为共享运营数据保持一致。

#### 菜单、选项与购物车（Tier 1）

<a id="fr-010"></a>

- **FR-010**: 员工主页面 MUST 默认展示当日已安排且上架的菜单，以卡片展示图片、英文名称、价格和菜系，并为无菜品、加载失败及图片失效提供可理解的英文状态。

<a id="fr-011"></a>

- **FR-011**: 菜品详情 MUST 展示描述、蛋白质来源、过敏原、辣度、选项组、是否必选及各选项加价；分类、辣度和过敏原使用本文定义的固定英文枚举。

<a id="fr-012"></a>

- **FR-012**: 员工 MUST 可多选菜系并搜索名称或描述关键词；菜系间取并集，菜系结果与关键词条件同时满足，搜索不区分大小写，清除条件后恢复相应菜单。

<a id="fr-013"></a>

- **FR-013**: 有配置的菜品 MUST 先完成必选项再加入购物车；选择选项时更新含加料单价，不能使用不属于该菜品的选项。

<a id="fr-014"></a>

- **FR-014**: 购物车 MUST 将同菜品同配置合并计数、不同配置分行，并展示每项已选配置；选项选择顺序不影响条目是否相同。同一浏览器刷新、关闭后重开及退出后重新登录同一账号须恢复草稿；不同账号隔离，恢复时重新校验配置、价格与可售性，不自动下单。

<a id="fr-015"></a>

- **FR-015**: 员工 MUST 能加减正整数份数与移除条目，实时看到总份数和总价；快速操作的结果必须与成功接受的操作一致，不得丢失已接受操作或突破数量限制。

#### 结算与订单（Tier 1）

<a id="fr-016"></a>

- **FR-016**: 结算 MUST 显示菜品、配置、数量、含加料的小计与总价，并允许选择配送日期、`Lunch` / `Dinner`、历史或新地址；默认日期为当天，再按截单规则调整。

<a id="fr-017"></a>

- **FR-017**: 下单前 MUST 校验非空购物车、非空有效地址、非过去配送日期、目标日期菜单可用性及已确认的价格和配置；失败不得生成部分订单，购物车保留并指出需调整项。

<a id="fr-018"></a>

- **FR-018**: 同一次结算提交的重复点击、并行尝试和结果丢失后的重试 MUST 只创建一个订单并返回同一个订单结果，不产生重复业务效果。

<a id="fr-019"></a>

- **FR-019**: 成功下单 MUST 创建 `Pending` 订单，展示唯一编号和配送日期、餐次、地址，保存本人的新地址，并移除本次已购买的购物车条目。

<a id="fr-020"></a>

- **FR-020**: 员工 MUST 能查看本人全部历史订单和详情，包含状态、各项配置及金额；菜品后续变更不得改变历史成交内容。

<a id="fr-021"></a>

- **FR-021**: 员工 MUST 仅能取消本人的 `Pending` 订单；成功后为 `Cancelled`，重复取消不重复产生效果，非法或与管理员处理冲突的取消明确反馈最终状态。

#### 订餐规则与偏好（Tier 2）

<a id="fr-022"></a>

- **FR-022**: 每单 MUST 最多 5 份餐品，按所有条目份数合计；达到上限时菜单添加按钮和购物车加号不可增加并解释原因，提交时同样必须执行该限制。

<a id="fr-023"></a>

- **FR-023**: 系统 MUST 按食堂运营时间判定截止：配送当日 10:00 起午餐不可订，15:00 起晚餐不可订；不依赖员工设备显示的时间。

<a id="fr-024"></a>

- **FR-024**: 已截单的当前餐次 MUST 自动选为时间上最近的可订餐次：当日 15:00 前为当日晚餐，否则为次日午餐，并明确通知；提交瞬间发生切换时，员工须确认新配送安排再提交。

<a id="fr-025"></a>

- **FR-025**: 每位员工同一配送日期、同一餐次 MUST 最多有一个 `Pending` 或 `Confirmed` 订单，包括同时提交；存在时将结算操作改为 `View Existing Order` 并打开该订单。

<a id="fr-026"></a>

- **FR-026**: 变更配送日期或餐次后 MUST 重新核验目标菜单、已选配置、价格和既有有效订单；不可用条目明确提示，不静默替换或删除，不绕过重复订餐限制。

<a id="fr-027"></a>

- **FR-027**: 员工 MUST 可保存、修改或清除过敏原、菜系、辣度、口味浓淡和单餐预算范围；预算为非负人民币金额且下限不得大于上限，未设置偏好不影响订餐。

<a id="fr-028"></a>

- **FR-028**: 普通加购 MUST 按菜品基础标签与已选选项标签的并集计算过敏原；命中本人标记时弹窗列出命中项，继续才加入，拒绝不改变购物车。配置变化出现新匹配时重新提醒；普通菜单不得据此过滤菜品。

<a id="fr-029"></a>

- **FR-029**: 菜单 MUST 提供 `Recommended for Me` 开关，开启时按菜系偏好优先、同组内辣度匹配优先排序并高亮匹配项；关闭恢复默认顺序，口味浓淡不作为强制排序条件。

<a id="fr-030"></a>

- **FR-030**: 购物车总价高于已设置预算上限时 MUST 在结算提示，但不得仅因超预算阻止提交；等于上限不算超出。

#### Console 与可演示数据（Tier 2）

<a id="fr-031"></a>

- **FR-031**: 管理员 MUST 在具有独立导航的 Console 中以表格查看菜品，并可搜索与按分类筛选。

<a id="fr-032"></a>

- **FR-032**: 管理员 MUST 可新增和编辑名称、描述、价格、分类、蛋白质、菜品基础过敏原、辣度、图片及配置组、选项加价和选项过敏原；上传须为可解码的 JPEG、PNG 或 WebP，单张不超过 5 MiB（5,242,880 字节）。无效内容不得保存，更换图片失败保留旧图并提供英文反馈。

<a id="fr-033"></a>

- **FR-033**: 管理员 MUST 可上架和下架菜品；下架后不再出现在员工获取的菜单中，也不能由旧购物车提交购买，已存在订单内容不变。

<a id="fr-034"></a>

- **FR-034**: 管理员 MUST 可设置指定日期的每日菜单，默认选择次日但允许当日，为每个菜品设非负整数供应量；不同日期的安排相互独立。

<a id="fr-035"></a>

- **FR-035**: 首次初始化 MUST 为运营今天和明天各安排 PRD 的 9 个示例菜品、配置及英文资料，每道初始供应 20 份，支持有效窗口内真实下单；重复执行不得重复数据、覆盖运营修改、重置库存占用或生成虚构收入。九道和二十份是项目采用的种子基线，不是原文强制数量。

<a id="fr-036"></a>

- **FR-036**: 管理员 MUST 可查看全部订单，执行 `Pending → Confirmed → Completed` 或 `Pending → Cancelled`；不允许回退、跳过确认或取消 Confirmed/Completed。已取消订单重复取消返回当前结果且不重复恢复库存；取消与确认并发仅一个转换成功。员工随后查看得到相同状态。

#### 库存与实时同步（Tier 3，必交付）

<a id="fr-037"></a>

- **FR-037**: 菜单 MUST 展示目标日期菜品剩余量；1–3 份为低库存，0 为售罄并不可添加或提交，购物车本身不占用库存。

<a id="fr-038"></a>

- **FR-038**: 下单 MUST 再次核验所有条目需求的每日库存，所有配置合计消耗同一菜品供应；并行购买不得超卖，任一条目不足则整单不创建、不扣减，并告知具体不足菜品及可用量。

<a id="fr-039"></a>

- **FR-039**: 已打开菜单的员工 MUST 无需手动刷新即可看到他人下单、取消或管理员调整导致的剩余量变化；断线恢复后恢复到最新数量。

<a id="fr-040"></a>

- **FR-040**: `Pending` 订单取消 MUST 一次性恢复对应日期、菜品、份数的库存；重试不重复恢复，已确认和已完成订单继续占用供应，管理员不得将供应总量调低到仍占用量以下。

#### AI 选餐（Tier 3，必交付）

<a id="fr-041"></a>

- **FR-041**: 员工 MUST 能输入英文自然语言诉求，获得基于个人偏好、目标日期可用菜单与近 7 天未取消订餐记录的推荐；未设置偏好或没有历史记录也可使用。

<a id="fr-042"></a>

- **FR-042**: 推荐 MUST 排除未上架、未安排、售罄，以及菜品基础标签或任一当前选项标签命中本人过敏原的整道菜；不因某次未选该选项而放宽 AI 排除。对近 7 天已点菜品降优先级，明确要求不重复时按要求排除，没有匹配候选时说明原因。

<a id="fr-043"></a>

- **FR-043**: 推荐 MUST 使用真实菜单菜品卡片并附英文个性化理由，内容逐步呈现；卡片可进入正常配置与加购流程，并遵守数量、过敏原提示和可用性校验。

<a id="fr-044"></a>

- **FR-044**: 推荐失败、超时或没有结果时 MUST 明确说明并允许恢复普通选餐，不影响核心下单；不得展示虚构的可购买菜品或以固定假结果宣称推荐成功。

#### 经营看板（Tier 3，必交付）

<a id="fr-045"></a>

- **FR-045**: Console MUST 默认展示运营今天的订单总数、收入、已完成/待处理/已取消数、按份数排名的菜品 Top 10 柱状图、午晚餐订单量及截至查询日的 7 个自然日订单量与收入折线图；所有指标的日期边界遵循 FR-047。

<a id="fr-046"></a>

- **FR-046**: 看板 MUST 展示查询日 D（默认运营今天）已安排且上架、剩余量不超过 3 的菜品列表，区分 0 与 1–3；读取 D 供应行在查询时的实际剩余量，不回放历史库存。统计来自实际订单与每日供应，并支持自动或显式手动刷新及显示查询日期和统计更新时间。

<a id="fr-047"></a>

- **FR-047**: 所有经营指标 MUST 按配送日期归属。看板接口以可选 `date` 为查询日 D，省略时取 Asia/Shanghai 运营今天；概览、Top 10、餐次分布及库存预警统一取 D，七日趋势为含首尾的 D-6 至 D，响应 `date` 回显 D，`generatedAt` 表示本次生成时间。订单总数及餐次分布包含全部状态，待处理为 `Pending` 加 `Confirmed`；收入和销量仅计 `Completed`，收入注明“Completed Order Amount”且不代表收款。销量合并同菜品不同配置，按份数降序、菜品 ID 升序取 Top 10，七日零数据日期仍显示。

### Key Entities *(include if feature involves data)*

- **User**: 具有唯一邮箱、受保护的密码凭据和员工/管理员角色；关联本人偏好、地址和订单。
- **Dietary Preference**: 用户所选过敏原、菜系、辣度、口味浓淡及可选预算上下限。
- **Delivery Address**: 用户保存的非空配送地址文本；历史订单保留当时选用的地址。
- **Dish**: 菜品名称、描述、图片、基础价格、分类、蛋白质来源、基础过敏原、辣度与上下架状态；选项单独维护过敏原。
- **Customization Group / Option**: 菜品可选配置，包含组名、是否必选、可选项及额外费用；区分单选配置与多选加料。
- **Daily Menu / Supply**: 指定配送日期安排的菜品、供应总量、已占用量和剩余量，所有餐次与配置共享该菜品当天供应。
- **Cart / Cart Item**: 员工待购买的菜品、配置组合、数量及当前金额；相同菜品与配置构成一个条目。
- **Order / Order Item**: 唯一订单编号、所属员工、配送日期、餐次、地址、状态、创建时间、总价，以及下单时各菜品和配置的名称、单价、份数与小计。
- **Recommendation**: 一次自然语言选餐诉求及基于当前可用菜品形成的推荐项与理由；不创建独立于真实菜单的商品。
- **Operating Metrics**: 从实际订单及每日供应汇总的日期指标、销量、餐次分布和库存预警，无独立手工填报的营业数据。

## Success Criteria *(mandatory)*

### Measurable Outcomes

<a id="sc-001"></a>

- **SC-001 — 订餐任务完成度**: 在 10 名首次使用者的验收任务中，至少 9 人无需协助即可在手机或桌面完成注册、选餐和下单，单人耗时不超过 5 分钟，并能准确指出配送日期、餐次和地址。

<a id="sc-002"></a>

- **SC-002 — 多端可用性与语言**: 在 375、768、1440 像素宽度下，全部员工流程（含 AI 选餐与库存查看）均可完成；逐页检查的系统提供文案及预置菜单内容 100% 为英文，用户自由地址保留原文，无遮挡关键操作或页面级横向滚动。

<a id="sc-003"></a>

- **SC-003 — 高峰体验**: 在 200 名同时活跃员工、500 个菜单菜品的验收场景中，95% 的菜单打开/筛选/搜索在 2 秒内显示可用结果，95% 的购物车操作在 0.3 秒内显示结果，95% 的有效下单在 3 秒内显示明确结果；不以省略业务校验换取速度。

<a id="sc-004"></a>

- **SC-004 — 金额与配置正确性**: 覆盖普通菜品、单选、多选、付费加料及混合数量的至少 20 个验收订单，配置保留正确率与金额精确到分的一致率均为 100%。

<a id="sc-005"></a>

- **SC-005 — 订餐规则正确性**: 数量为 0/1/5/6、各截单边界、跨日、无菜单、价格变化及同餐次有效订单场景全部得到预期结果；同一次提交并行重试 20 次只产生一个订单，两个独立提交竞争同餐次时最多产生一个有效订单。

<a id="sc-006"></a>

- **SC-006 — 隐私与持续保存**: 账号、偏好、地址、菜单、每日库存和订单在正常重启后全部可恢复；未授权账号访问个人记录或 Console 的验收尝试 100% 被拒绝，刷新保持登录、退出后受限访问失败。

<a id="sc-007"></a>

- **SC-007 — 运营自助能力**: 管理员无需修改程序即可在 5 分钟内新增菜品、上传图片、安排次日供应并完成上下架；员工重新打开菜单后 2 秒内看到已生效结果；合法订单状态变化与员工所见一致。

<a id="sc-008"></a>

- **SC-008 — 提醒可理解性**: 至少 9/10 名验收使用者能正确解释过敏原警告与预算提示的含义，以及是否可以继续；全部命中过敏原的加购场景得到提醒，超预算但其他条件有效的订单可以成功提交。

<a id="sc-009"></a>

- **SC-009 — 库存**: 初始 10 份供应由 20 名员工同时各购买 1 份时最多成功 10 份、剩余量不为负；取消后准确恢复；95% 的已连接菜单页面在库存变更后 2 秒内显示新数量。

<a id="sc-010"></a>

- **SC-010 — 推荐**: 至少 20 组包含过敏原、售罄、预算和近期订单的功能诉求中，推荐 100% 指向真实可售且无过敏原冲突菜品。性能另以预先登记的至少 20 次有有效候选、预期 COMPLETE 的正常请求为固定样本，首张有效卡片呈现 p95 ≤5 秒、完整完成 p95 ≤20 秒；全部尝试计入分母，缺首卡或未 COMPLETE 的对应耗时计为正无穷，不得事后剔除失败。预期 NO_MATCH、澄清与故障用例独立核验，不纳入首卡性能样本；分组和计时遵循流契约 3.4。至少 8/10 名使用者认为理由与个人诉求相关。

<a id="sc-011"></a>

- **SC-011 — 经营统计**: 对至少覆盖连续 7 天、四种订单状态和不同配置的已知订单样本，分别验证省略 date 的运营今天及显式 date 为非今天的 D；看板所有指标统一取各自查询日，趋势覆盖该日及前六日，每个计数、金额、销量和库存预警与独立核算 100% 一致；刷新后 3 秒内反映已完成的订单变化。

## Assumptions

<a id="a-001"></a>

- **A-001 — 范围与评审**: 用户已明确要求无开发时限、全部功能实现，因此 Tier 1、Tier 2、Tier 3 均为本次必交付范围；FR-001–047 与 SC-001–011 全部为验收门槛。该范围是用户决定，不是待确认假设；面试评分细则不作为产品内功能，也不豁免任何模块。

<a id="a-002"></a>

- **A-002 — 运营时间**: 默认食堂位于中国大陆，采用 `Asia/Shanghai`；不添加周末、节假日或提前订餐天数限制。未来餐次须已有菜单才可成交。未指定餐次默认当日午餐，再按截止规则调整。

<a id="a-003"></a>

- **A-003 — 自动切换**: PRD 要求自动切换“选择”，本规格将其解释为更新结算中的日期和餐次并通知用户，而不是在用户不知情时生成另一餐次订单；提交时才发生切换则需确认新安排。

<a id="a-004"></a>

- **A-004 — 选项规则**: 面胚、酱料、面型和主食为组内单选；加料可多选，每种每份最多选择一次。必选组至少选定一项；同配置的选项比较不受点击顺序影响。总价仅含菜品和选项，不额外添加运费、税费或折扣。

<a id="a-005"></a>

- **A-005 — 默认菜单顺序**: 未开启偏好排序时按英文名称升序；偏好排序同等匹配时沿用此顺序。每日菜单可覆盖午晚两餐，每日供应按菜品共享，不为不同配置或餐次建立额外份额。

<a id="a-006"></a>

- **A-006 — 管理员与状态**: 管理员由运营方预置，不允许自助提权；补齐订单列表、确认、完成和 Pending 取消。Completed/Cancelled 不占有效餐次名额；Completed 仍占供应。管理员重复取消成功返回原状态，其他重复或非法状态转换按接口冲突处理。不扩展退款、批量调度或任意改价改单。

<a id="a-007"></a>

- **A-007 — 数据与素材**: 采用九道样例、今天及明天各 20 份/菜作为项目种子基线；原文约 50 道是背景，500 道是自定增长验收规模。原始图片包已在 `/Users/zhoubo/Downloads/WeBox-PRD-候选人交付包/webox_product_images.zip` 找到并验证，包含 20 张图片；实施时建立九道菜的图片映射并复制所需资源到交付项目，记录来源，不要求用完全部图片。

<a id="a-008"></a>

- **A-008 — 日期和库存衔接**: 结算日期变化后按该日期菜单重新校验；不假设未来必有同款菜品，也不自动生成明日菜单。管理员设置供应数量、剩余量展示、实时同步、扣减、防超卖及取消恢复均须完整交付，Tier 分层只保留来源分类含义。

<a id="a-009"></a>

- **A-009 — 模块依赖**: 推荐的售罄排除、看板的剩余量预警依赖准确的每日库存记录。规划必须同时覆盖库存核验、扣减、取消恢复及菜单实时同步，并使推荐和看板读取一致的可用量；不得把配置的供应总量冒充剩余量。

<a id="a-010"></a>

- **A-010 — 推荐时间与过敏原**: “近 7 天”为运营今天及前 6 个自然日的非取消配送记录；默认软排重，明确诉求按指定日期硬排除。菜品基础标签和选项标签分别录入；普通加购按实际配置并集提醒，AI 按基础及所有当前选项的并集保守排除。管理员录入已知成分，空标签只表示未标记，不承诺绝对安全，不根据菜名推断真实成分。

<a id="a-011"></a>

- **A-011 — 经营口径**: PRD 未定义收入和日期归属；项目采用配送日、仅 Completed 的含加料订单金额，展示为 Completed Order Amount，不等同收款。Top 10 按同样状态累计份数，合并配置，销量相同按菜品 ID；不足十道显示实际数量，历史名称来自计入统计的订单快照。

<a id="a-012"></a>

- **A-012 — 验收目标**: 原文约 200 名员工不等于 200 并发；原文未提供性能和任务耗时数字，200 同时活跃会话、500 菜品及 SC-001/003/007/009/010/011 中的数值为规划与验收基线，适用于稳定办公网络和可用依赖；正常持久化验收不等同于断电灾难恢复承诺。后续若调整基线须同步规格。

<a id="a-013"></a>

- **A-013 — 输入限制**: PRD 未具体规定的文本上限默认为菜品/配置名称 100、描述 2000、蛋白质来源 200、推荐诉求 1000 个字符；必填文本去除首尾空白后不得为空，密码按原输入验证且不截断。菜品图片默认接受 JPEG、PNG、WebP，单张最多 5 MiB（5,242,880 字节）；这些是本规格补充的验收边界。

<a id="a-014"></a>

- **A-014 — 交付与治理依赖**: 交付要求以 [delivery-constraints.md](delivery-constraints.md) 为入口；用户补充的无开发时限、全部功能必交付优先，其余要求以 PRD §7 原文为准；当前 `.specify/memory/constitution.md` 仍为占位模板，未提供已批准的额外原则。图片资源已定位且待实施时导入；原始 AI 编程对话导出、推荐服务与运行环境仍须落实，不宣称本规格已经提供可运行产品。
